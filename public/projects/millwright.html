Millwright

Let an AI author CNC toolpaths — without ever letting it drive the machine unsafely.

Domain CAM / CNC automation Stack Python · MCP · Fusion 360 API Role Solo architect & builder Started Jun 2026

Summary

Millwright is a bridge that lets a large language model author CAM operations directly in Autodesk Fusion 360 — recognising machinable features and generating toolpaths through the Model Context Protocol. It's the manufacturing-automation counterpart to my robotics work: applying agentic AI to a real machine tool.

The whole design is organised around one principle: the AI can plan, but it can never move the machine unsupervised. All motion stays gated behind a deterministic preflight and an explicit human arming step — a hard boundary the LLM path cannot cross.

Design & system architecture

Engineering highlights

Safety kept out of the AI path

Motion gating lives entirely in a deterministic preflight plus a human ARM step — never in the LLM-driven code — so an authoring mistake can't become machine motion.

A rigorous preflight

Tracks G90/G91 modal state, computes true arc bounding boxes, checks the work envelope, and warns on cutter-comp and unverifiable offsets before a job is allowed to run.

De-risked, transport-first

The full LLM→MCP→localhost→Fusion path was proven with a ping round-trip before any authoring tool shipped — the hard integration risk retired first.

Phased capability rollout

Feature recognition opens one class at a time — holes, then pockets, then contours — each gated on a real-part track record through the full build order.

Fail-safe execution

The run monitor drives the job over CNCjs with automatic feed-hold and stop on fault or a socket disconnect, rather than assuming a clean channel.

Clean secrets hygiene

No secrets in the repo: the bridge secret and CNCjs token are read from the environment via Doppler, with config kept git-ignored.

Showcase — challenges I overcame

1

Letting an LLM near a machine tool without letting it crash one

Challenge
An LLM authoring toolpaths is powerful and non-deterministic — exactly the wrong properties for something that can drive a spindle into a fixture at feed rate. A single bad move is real, physical damage.
Approach
I put a hard boundary between planning and motion: the LLM only authors: every job passes a deterministic preflight (envelope, arc bounds, modal state) and then waits for an explicit human ARM. None of that safety code sits in the AI path.
Outcome
An authoring mistake cannot become machine motion — the AI can plan all day, but a human and a deterministic check stand between it and the spindle.
2

Retiring the scariest integration risk first

Challenge
The riskiest unknown wasn't the CAM logic — it was whether an LLM could even reach into a live Fusion 360 session over MCP at all. Building authoring tools on top of an unproven transport risks a total rewrite.
Approach
I built the pipeline transport-first: proved the full LLM→MCP→localhost→Fusion path with a bench ping round-trip before writing a single authoring tool.
Outcome
The hardest integration risk was retired at step one, so every feature since builds on a channel that's known to work.
3

Not letting the AI's reach outrun its track record

Challenge
It's tempting to open up holes, pockets, and contours all at once — but each feature class is a new way to author a bad path, and unproven breadth is just accumulated risk.
Approach
I gated capability behind a phased rollout: holes first, then pockets, then contours — each class only opens once it has earned a track record on real parts through the full build order.
Outcome
The AI's authoring reach grows only as fast as it's proven, so capability and trust expand together rather than on faith.
