Crawler1

A compact skid-steer robotics platform — and an autonomy testbed built on a proven core.

Domain Field robotics Stack ROS2 · Arduino · Gazebo Role Solo architect & builder Started Jun 2026

Summary

Crawler1 is a small ROS2/Arduino skid-steer robot with two jobs: local autonomous path-following as the primary mode, and long-range teleoperated photo capture as the secondary. It doubles as a low-stakes testbed for autonomy work that later benefits the larger Forager1 robot.

What makes a days-old project already credible is disciplined reuse: it was bootstrapped from Forager1's proven navigation and simulation core, with a provenance ledger recording exactly what was adapted and from which commit.

Design & system architecture

Engineering highlights

Provenance-tracked reuse

A PORTABLE.md ledger records every file adapted from Forager1 and the commit it came from — reuse with an audit trail, not copy-paste.

Simulation-first

A Gazebo Harmonic world (full and headless/no-render variants) lets the drive loop and bridge be validated before hardware exists.

Planned before built

A v0.2 System Requirements doc and BOM, plus 25 dependency-ordered tasks dated to a Nov-2026 milestone and synced to a calendar — maturity uncommon for a project this young.

Consistent platform conventions

The ROS2 workspace mirrors Forager1's layout (colcon root, twist-mux, launch structure) so lessons and tooling transfer directly between the two robots.

Showcase — challenges I overcame

1

Reusing a proven robot without inheriting a copy-paste mess

Challenge
Bootstrapping from Forager1 is the fast path — but copy-paste reuse rots fast: six months on, nobody knows which files were adapted, from when, or whether an upstream fix ever made it across.
Approach
I treated reuse as a first-class artifact. A PORTABLE.md provenance ledger records every adapted file and the exact Forager1 commit it came from, and the workspace mirrors Forager1's layout so tooling transfers directly.
Outcome
A days-old project is already credible: the lineage is auditable, not guesswork, and lessons flow both ways between the two robots.
2

Making progress before any hardware exists

Challenge
Waiting on a BOM and a physical build would stall all software work — and I wanted the drive loop de-risked long before parts arrived.
Approach
I stood up a Gazebo Harmonic skid-steer world with a diff-drive plugin and IMU, in both full and headless/no-GPU variants, so the drive path and bridge run anywhere — even inside a sandbox.
Outcome
Simulation and infrastructure shipped first; hardware bring-up starts against already-exercised software rather than a blank slate.
3

Two modes that must never fight for the motors

Challenge
Autonomous path-following and long-range teleop capture both want to command the base — and an operator must always be able to take over instantly.
Approach
Command arbitration runs through twist-mux with teleop at higher priority than autonomy, and mission state is carried over a Bluetooth link — the same pattern proven on Forager1.
Outcome
Autonomy is primary, capture rides along, and a human override always wins — deterministically, at the mux.
