Domain Field robotics Stack ROS2 · Python · C++ · Arduino Role Solo architect & builder Started Mar 2026

Summary

Forager1 is a self-driving outdoor robot for agricultural terrain, built on ROS2. It navigates by GPS waypoints, fuses IMU and wheel odometry through an extended Kalman filter, and drives a skid-steer base — all under a two-layer safety architecture that splits soft, high-level planning on a Raspberry Pi from a hard, deterministic safety layer on the motor-control firmware.

The point of the project isn't just to make a robot move — it's to build it the way a funded robotics team would: versioned system requirements, a traceable safety contract, hundreds of regression tests, and a project schedule that lives in my calendar.

Design & system architecture

Engineering highlights

Safety-first by design

A latching e-stop, direction-aware proximity gating, sensor-liveness supervision, and a micro-ROS reconnect state machine that forces motors stopped whenever the agent link isn't confirmed connected.

Formal, traceable requirements

A versioned System Requirements document (v0.11) with SYS-SAF / SYS-HW / SYS-PWR requirement IDs, a firmware↔Pi safety contract, and a dated requirements-audit trail.

Calendar-driven schedule

A structured plan file renders to a gantt and syncs task dates into Google Calendar, keeping a solo build accountable to real milestones.

Tested like production

298 automated tests cover the e-stop round-trip, IMU ENU conversion, battery state-of-charge logic, and goal-retry limits — regressions get caught, not shipped.

Clean hardware/software seam

A Python nav stack and a C++ ros2_control hardware interface, split so the safety-critical layer stays deterministic and independently reasoned about.

Designed to interoperate

A bridge exposes a clean operator-console contract (mission JSON + telemetry topics) so the Pathfinder app can drive it without touching the proven mission sequencer.

Showcase — challenges I overcame

1

Making "safe" a property of the hardware, not the software

Challenge
A moving outdoor robot can't depend on a Linux process staying alive. If the Pi hangs, a Wi-Fi link drops, or a node crashes mid-drive, the motors must stop — and no high-level bug can be allowed to override that.
Approach
I split control into two layers with an explicit safety boundary: soft planning on the Pi, a hard latching e-stop and motion gating in Arduino firmware. A micro-ROS reconnect state machine forces motors stopped unless the agent link is confirmed connected.
Outcome
Loss of the link or a latched fault stops the robot at the lowest layer — the Pi physically cannot drive through it. The e-stop round-trip is covered by automated tests.
2

Trusting the robot before it existed as hardware

Challenge
Debugging navigation, localization drift, and heading conventions on real hardware is slow and can be destructive — but I needed confidence the whole loop was correct before spending on a build.
Approach
I stood up a Gazebo Harmonic world and validated the entire drive loop in sim — clock, wheel odometry, the TF tree, EKF fusion of GPS/IMU/odom in REP-103 ENU, GPS waypoint sequencing, and twist-mux priority — against a 298-test regression suite.
Outcome
Phase 2 is simulation-validated end-to-end, so hardware bring-up starts from a known-good software stack rather than a blank slate.
3

Running a solo build like a funded program

Challenge
Solo projects drift — scope creeps, "done" gets fuzzy, and there's no one to hold the schedule. I wanted the rigor of a real robotics team without the team.
Approach
I wrote a versioned System Requirements document with traceable SYS-SAF/HW/PWR IDs and a firmware↔Pi safety contract, and put the schedule in a structured plan file that renders a gantt and syncs task dates into my Google Calendar.
Outcome
Every requirement is traceable, every phase has a testable Definition of Done, and the plan runs against real calendar deadlines — 33 of 96 tasks done and dated.
