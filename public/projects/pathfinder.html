Pathfinder

Draw a field on your phone; hand the robot a mission.

Domain Mobile / robotics ops Stack React Native · Expo · Mapbox Role Solo architect & builder Started Jun 2026

Summary

Pathfinder is the operator's console for the Forager1 robot: a React Native / Expo app where you draw a field coverage area, mark exclusion zones and a home point on a map, and generate a complete robot mission from it.

The interesting engineering isn't the drawing UI — it's the contract. Before writing delivery code, I read the Forager1 codebase at source level and froze the real interface it expects, then designed Pathfinder to be robot-agnostic: supporting a second robot means adding a profile, not forking the app.

Design & system architecture

Engineering highlights

Interface reconciliation, done right

Rather than assume an API, I read the robot's codebase and discovered it has no network receiver — it ingests mission files at launch. The contract was frozen against that reality.

Robot-agnostic by design

Delivery is per-transport adapters; planner, pattern, and coordinate frame are profile-driven. A second robot is a new profile, not a fork of the app.

Requirements with a Definition of Done

A master spec ties each phase to PRD items and a testable completion condition, so "done" is defined per phase rather than felt.

An explicit performance budget

Scale/perf targets SP1–SP8 pin the area ceiling, vertex/zone/waypoint limits, and generation-time budgets — turning vague "should be fast" into numbers you can test.

Cost-constrained from the start

The design commits to staying within free-tier Mapbox and networking limits for the MVP, a real constraint baked into the architecture rather than discovered later.

Consistent design system

A NativeWind theme mapped to the shared "Console" palette keeps the app visually of a piece with the rest of the portfolio, on both web and native builds.

Showcase — challenges I overcame

1

The robot I was building for had no API to talk to

Challenge
I assumed I'd POST a mission to Forager1 over the network. Reading the robot's source proved there was no receive endpoint — it only ingests mission files at ROS2 launch.
Approach
I stopped guessing and treated the robot's real launch inputs as the specification. I froze a file-based contract — mission.json + site.geojson in WGS-84 — and delivered it over scp, matching what the robot already does.
Outcome
Zero glue code on the robot. Pathfinder produces artifacts Forager1 already knows how to read, so the two integrate without modifying the proven robot stack.
2

Not hard-wiring the app to a single robot

Challenge
The fastest path was to bake Forager1's schema, coordinate frame, and transport straight into the screens — and be stuck the moment a second robot appeared.
Approach
I pushed everything robot-specific behind a profile: pattern planner, coordinate frame, and a per-transport delivery adapter. The UI only ever speaks the abstract mission model.
Outcome
Supporting another robot is a config file, not a fork — the agnostic-by-design goal is structural, not aspirational.
3

Keeping "fast" and "cheap" testable, not vibes

Challenge
Coverage math on a phone can blow up with big fields, and a naive map integration can quietly leave the free tier and start costing money.
Approach
I wrote an explicit budget — SP1–SP8 scale/perf targets capping area, vertices, zones, waypoints, and generation time — and committed the MVP to free-tier Mapbox and networking limits up front.
Outcome
Performance and cost became numbers I can test against rather than surprises discovered in the field.
